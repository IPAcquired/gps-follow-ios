# Approved CORVON743V2 firmware updates

The operator can use the Orange Pi's two-way native UART connection to prepare an SD-card firmware update. ArduCopter handles the file transfer while running. Its bootloader reads the card after the owner power cycles the controller. This link connects Pi UART0 to controller UART4. Bootloader recovery uses the controller's USB or USART1 console.

Only the fixed firmware actions in the companion maintenance manager may call `run_firmware`. They share ownership of the port with the existing passive monitor. The firmware module opens no serial port of its own and schedules no work. The operator should use a disarmed aircraft on the bench with reliable power. Ground-state and identity checks stay active.

1. **Prepare.** The worker checks the installed release recipe, bootloader identity and card root, reads current firmware and parameter storage, and saves both backups in a new private directory on the Pi. It returns the proposed release, package digest, prior state and an approval digest. Preparing changes no aircraft files. If the approved bytes are already installed, it reports that outcome without proposing another flash.
2. **Apply after review.** Compare the proposal with the reviewed public release, then submit its exact approval digest within 15 minutes. The worker rechecks the live aircraft and backups, transfers the fixed package under a unique inactive name, and reads the entire file back. It promotes the verified file to `/ardupilot.abin` only after those checks pass. The next time the board enters its SD-capable bootloader, that filename authorizes programming. Treat the rename as the commit point.
3. **Power cycle.** The owner removes all controller power, then restores it with the microSD still inserted. Leave power connected during programming. The full cycle also resets the BMP581 sensor on this board. The controller may temporarily disappear from telemetry. The worker never sends a reboot command.
4. **Verify.** The worker checks the normal disarmed, grounded controller and expected bootloader, compares the full installed application to the reviewed bytes, checks the telemetry and logging settings, reads a healthy barometer, and verifies `/ardupilot-flashed.abin` on the card. Flight readiness requires the aircraft's separate setup and bench checks.
5. **Clean up.** An explicit cleanup with the original approval digest removes only this transaction's verified successful marker. Keep the private backups. If a verification or partial-flash marker remains, preserve it for diagnosis. After an ambiguous rename acknowledgement, verify or inspect the existing card state before another write. USB/DFU is the recovery path if the runtime UART does not come back.

## Versioned release recipes

This revision trusts the specific board, firmware package and digest published in its release manifest. The handler itself contains the reviewed SHA-256 pins. Substituting files or editing the manifest alone cannot authorize other firmware. The ABIN body matches the APJ's independently checked application bytes. Its header matches the pinned upstream packager and the original board build's recorded MD5. The bootloader's MD5 is an integrity check. The trusted SHA-256 pins and exact operator-approved proposal identify the release and target.

For a future update, select a named release from the project's canonical repository and install a matching, reviewed recipe into the root-owned worker deployment. The release maintainer must compare the proposed board ID, APJ and decompressed application digests, upstream commit, bootloader, flash layout, and bootloader-format ABIN with the independently reviewed build. They then update the package constants, source and target version guards in the firmware and serial worker, board validation tests, and release manifest together. Rerun the transaction and transfer tests and publish the new recipe with its APJ, ABIN and checksums. The owner reviews that version before enabling it on the Pi. Ordinary prepare/apply then produces a separate fresh, device-bound proposal. A new tag or mutable network manifest never changes the trusted version automatically. ## Board and update boundaries

Two full device flash reads matched the official CORVON743V2 bootloader, including the four SD-update filenames. The live bootloader reported board ID 1229 and 1,703,936 bytes of application flash. Its erase interval starts at 0x08020000 and ends just before 0x081C0000. Programming can erase all thirteen application sectors, including prior diagnostic data there. The first 128 KiB bootloader and final two 128 KiB parameter sectors sit outside that interval. The card bootloader advances through `ardupilot-verify.abin`, `ardupilot-flash.abin`, and `ardupilot-flashed.abin`. The worker refuses a pre-existing trigger or result. [Bootloader code](https://github.com/ArduPilot/ardupilot/blob/d9c5097c/Tools/AP_Bootloader/flash_from_sd.cpp) · [SD update guide](https://ardupilot.org/copter/docs/common-install-sdcard.html)

The host transaction tests simulate successful promotion, a separate boot, full verification and cleanup, as well as stale approvals, wrong targets or bootloader bytes, corrupted transfers, interruption, and ambiguous acknowledgements. The separate network-isolated SITL transfer test exercises the actual ArduPilot MAVFTP service with an inactive filename. Hardware bootloader behavior was checked against the captured binary and upstream code. No live SD firmware update was performed for these tests.
